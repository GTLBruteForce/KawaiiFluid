01 출발점/2026-01-12 이전 · bda2c03

고정 슬롯 해시 그리드가 걸어둔 두 개의 제약

SPH 유체는 매 프레임 입자마다 반경 h 안의 이웃 수십 개를 찾아 밀도·압력을 푼다. 입자 10만 개면 한 프레임에 수백만 번의 이웃 후보 읽기가 발생하고, 시뮬레이션 시간의 대부분이 여기서 나온다.

도입 전에도 uniform grid는 있었다. 셀 좌표를 큰 소수 세 개로 해싱해 65,536개 버킷 중 하나로 보내고, 버킷마다 16칸 고정 배열에 입자 인덱스를 적어두는 구조였다. 문제는 이 구조가 정확성과 성능 양쪽에 각각 제약을 걸고 있었다는 점이다.

{

    return h & (SPATIAL_HASH_SIZE - 1);          // 65,536 buckets

정리하면 두 가지다.

  • 정확성 — 셀당 16칸 상한. 초과분은 오류 없이 이웃 목록에서 빠진다. 해시 충돌로 서로 다른 셀이 같은 버킷을 쓰면 이 16칸 경쟁이 더 심해진다.
  • 성능 — 입자 데이터 자체는 공간 순서와 무관하게 배치되어 있다. 후보 인덱스를 얻어도 실제 읽기는 버퍼 전역을 뛰어다닌다.

두 문제의 뿌리는 같다. 입자 배열의 순서가 공간과 아무 관계가 없다는 것. 그래서 배열 순서 자체를 공간 순서로 바꾸기로 했다.

02 자료구조/Morton code · Z-Order curve

3D 좌표를 순서가 있는 정수 하나로

배열을 공간 순으로 정렬하려면 3D 좌표에 1차원 순서를 줘야 한다. 그냥 z*W*H + y*W + x로 펼치면 x축 이웃은 붙지만 y·z축 이웃은 한 행/한 면만큼 멀어진다.

Morton code는 각 축의 비트를 한 칸씩 어긋나게 끼워 넣는다. 상위 비트가 세 축 모두에서 먼저 비교되기 때문에, 코드 값이 가까운 두 셀은 세 축 모두에서 가깝다. 구현은 시프트와 마스크뿐이라 GPU에서 몇 사이클이면 끝난다.

03 도입/2026-01-12 · 7470af5 · +3,067줄

매 프레임 도는 5단계 GPU 정렬 파이프라인

정렬은 CPU로 내릴 수 없다. 입자 버퍼는 GPU에만 있고, 매 프레임 모든 입자가 움직이므로 정렬도 매 프레임 처음부터 다시 해야 한다. 그래서 Morton 코드 계산부터 셀 구간 구축까지 전부 compute shader로 묶었다. FKawaiiFluidZOrderSortManager가 1~4단계의 패스 등록과 중간 버퍼 수명을 맡고, 5단계는 그 결과를 쓰는 solver다.

각 단계가 무엇을 무엇으로 바꾸는지만 먼저 보면 이렇다 — 위치 → 정수 키(1) → 키 → 순서(2) → 순서 → 실제 메모리 배치(3) → 배치 → 셀별 구간표(4) → 구간표 → 이웃 목록(5).

1단계 · Morton 코드 계산

입자 하나에 스레드 하나. 하는 일은 연속 좌표를 정수 격자로 양자화하고, 그 격자 좌표를 2장의 방식으로 정수 키 하나로 접는 것이다. floor(pos / CellSize) 한 번으로 "두 입자가 같은 셀인가"를 정수 비교로 판정할 수 있게 된다.

출력은 배열 두 개다. 키 배열과, 0, 1, 2, …, N-1로 채운 인덱스 배열. 다음 단계의 정렬은 이 두 배열을 한 몸으로 움직인다 — 키는 정렬 기준으로, 인덱스는 딸려가는 짐으로. 정렬이 끝나면 인덱스 배열은 "새 자리 → 옛 자리"를 알려주는 순열이 되어 있다.

여기에 이 파이프라인 전체를 지탱하는 불변식이 하나 있다. XPBD/PBF 계열 solver는 한 프레임 안에서 예측 위치를 먼저 만들고 그 위에서 제약을 푼다. 그래서 격자를 만들 때 쓰는 좌표와 solver가 이웃을 찾을 때 쓰는 좌표가 같아야 한다. 현재 위치로 격자를 만들고 예측 위치로 탐색하면, 셀 경계를 막 넘은 입자들이 매 프레임 조용히 이웃을 잃는다.

uint Idx = DispatchThreadId.x;               // 스레드 하나 = 입자 하나

// solver가 이웃 탐색에 쓰는 것과 '같은' 좌표여야 한다
float3 Pos = Particles[Idx].PredictedPosition;

// 연속 좌표 → 정수 셀 좌표
int3 CellCoord = int3(floor(Pos / CellSize));

uint SortKey;
if (bUseHybridTiledZOrder)
{
    SortKey = ComputeHybridTiledKey(CellCoord);           // Hybrid 모드
}
else
{
    int3 GridMin = int3(floor(BoundsMin / CellSize));     // 격자 원점
    SortKey = Morton3DFromCell(CellCoord, GridMin);
}

MortonCodes[Idx]     = SortKey;
ParticleIndices[Idx] = Idx;      // 아직 아무것도 섞이지 않은 순열

2단계 · 라딕스 정렬

키가 고정 폭 정수라서 비교 정렬을 쓸 이유가 없다. GPU에서 흔한 비교 정렬(bitonic)은 O(N log²N)번의 패스가 필요한 반면, LSB radix sort는 키의 비트 폭 ÷ pass당 비트 수번이면 끝난다. 21비트 키에 pass당 8비트면 3회다.

한 pass는 키의 하위 R비트만 보고 세 가지를 한다 — 값별로 개수를 세고(histogram), 그 개수를 누적해 각 값이 출력 배열의 어디서 시작할지 계산하고(prefix sum), 그 오프셋대로 원소를 흩뿌린다(scatter). 이 정렬은 안정 정렬이라 다음 pass가 상위 비트를 처리해도 이전 pass가 만든 순서가 동률 구간 안에서 보존된다. 그래서 하위 비트부터 차례로 올라가는 것만으로 전체 키가 정렬된다.

scatter는 제자리에서 못 하므로 버퍼 두 개를 번갈아 쓴다(ping-pong). pass 수가 홀수면 결과가 임시 버퍼에 남으므로, pass 수를 짝수로 올림해서 결과가 항상 원래 버퍼에서 끝나도록 맞췄다 — 한 번 더 도는 비용으로 호출부의 분기를 없애는 거래다.

// 키의 유효 비트 수에서 pass 수가 결정된다
int32 SortKeyBits = bUseHybridTiledZOrder

if (RadixSortPasses % 2 != 0)

    RadixSortPasses++;   // ping-pong이 원래 버퍼에서 끝나도록 짝수로
}

for (int32 Pass = 0; Pass < RadixSortPasses; ++Pass)
{
    const int32 BitOffset = Pass * GPU_RADIX_BITS;

3단계 · 입자 재배치

2단계까지 알아낸 것은 "누가 몇 번째로 와야 하는가"뿐이다. 입자 데이터는 아직 원래 자리에 그대로 있다. 여기서 멈추고 순열만 들고 이웃 탐색을 하면, 후보를 좁히는 데는 성공하지만 읽기는 여전히 버퍼 전역을 뛴다 — 1장의 문제 그대로다. 그래서 이 단계에서 입자 구조체(64바이트) 자체를 새 버퍼로 옮겨 적는다.

방향이 중요하다. 스레드는 출력 슬롯을 맡고, 자기 슬롯에 올 입자를 옛 버퍼에서 끌어온다(gather). 그래서 쓰기는 완전히 연속이고 흩어지는 것은 읽기뿐이다.

이 한 번의 복사가 이 파이프라인이 하는 거래의 전부다. 무작위 접근을 입자당 프레임에 한 번으로 몰아넣고, 그 대가로 뒤따르는 solver가 입자당 수십 번 반복하는 이웃 읽기를 전부 연속 접근으로 바꾼다. SPH는 한 프레임에 solver iteration을 여러 번 도는 데다 밀도·압력·점성이 같은 이웃을 반복해서 읽으므로, 한 번 치르고 수십 번 회수하는 쪽이 이긴다.

KawaiiFluidSortingPipeline.usf · ReorderParticlesCS3단계
uint NewIdx = DispatchThreadId.x;            // 스레드 하나 = '출력' 슬롯 하나
uint OldIdx = SortedIndices[NewIdx];

SortedParticles[NewIdx] = OldParticles[OldIdx];   // 쓰기는 연속, 읽기만 흩어진다

// 입자와 나란히 유지되는 다른 per-particle 배열도 같은 순열로 함께 옮긴다.
// 하나라도 빠뜨리면 인덱스가 어긋나 엉뚱한 입자의 데이터를 읽게 된다.
if (bReorderAttachments != 0)
{
    SortedBoneDeltaAttachments[NewIdx] = OldBoneDeltaAttachments[OldIdx];
}

4단계 · 셀 구간 구축

정렬이 끝나면 같은 셀의 입자는 배열에서 반드시 연속이다. 그러면 셀마다 "어디서 시작해 어디서 끝나는지" 두 정수만 있으면 되고, 1장의 고정 슬롯 배열은 통째로 사라진다.

경계를 찾는 방법은 자기 키와 바로 앞 키를 비교하는 것뿐이다. 다르면 자기 자리가 새 셀의 시작이고 동시에 앞 셀의 끝이다. 스레드끼리 조율할 필요가 없어 한 번의 dispatch로 끝난다. 앞 단계와 달리 이 dispatch는 입자 수가 아니라 셀 수만큼의 배열에 쓴다는 점만 다르다 — 그래서 매 프레임 먼저 CellStart/CellEnd 전체를 "빈 셀" 표식(0xFFFFFFFF)으로 지우고 시작한다. 지우지 않으면 이번 프레임에 비어버린 셀이 지난 프레임의 구간을 그대로 가리킨다.

KawaiiFluidSortingPipeline.usf · ComputeCellStartEndCSAfter
uint CurrentCode = SortedMortonCodes[Idx];
uint CellID      = CurrentCode & (MAX_CELLS - 1);

if (Idx == 0)
{
    CellStart[CellID] = Idx;
}
else
{
    uint PrevCellID = SortedMortonCodes[Idx - 1] & (MAX_CELLS - 1);
    if (CellID != PrevCellID)
    {
        CellStart[CellID]   = Idx;        // 여기서 새 셀이 시작하고
        CellEnd[PrevCellID] = Idx - 1;    // 앞 셀은 직전에서 끝난다
    }
}

if (Idx == ParticleCountBuffer[6] - 1)   // 마지막 입자 — GPU가 기록한 실제 개수
{
    CellEnd[CellID] = Idx;
}

5단계 · 이웃 탐색

앞의 네 단계가 만든 것을 실제로 쓰는 쪽이다. 입자마다 자기 셀을 구하고, 그 주변 셀들의 구간을 훑는다. 훑을 셀의 범위는 CellRadius = ceil(SmoothingRadius / CellSize)로 정해진다 — SPH의 영향 반경 h가 몇 개의 셀에 걸치는지다.

여기서 5장의 Auto Cell Size가 왜 성능 결정이었는지가 드러난다. CellSize == h로 묶어두면 CellRadius가 1이 되고, 후보는 3×3×3 = 27셀로 고정된다. 이 값이 최적인 이유는 양쪽으로 밀어보면 보인다.

  • 셀을 h보다 작게 잡으면 반경이 2로 올라가 후보 셀이 125개가 된다 — 셀 조회와 구간 진입 비용이 그만큼 늘어난다.
  • 셀을 h보다 크게 잡으면 후보 셀은 27개 그대로지만 셀 하나의 부피가 커진다. 반경 밖 입자가 후보에 잔뜩 섞여 들어와 거리 검사에서 버려진다.

CellSize == h가 두 낭비가 만나는 지점이다. 사용자가 CellSize를 직접 만지던 시절엔 이 지점이 우연에 맡겨져 있었다.

후보 셀의 cellID를 구할 때는 1단계와 완전히 같은 키 함수를 써야 한다. 격자를 만든 규칙과 조회하는 규칙이 한 글자라도 어긋나면 존재하는 이웃을 못 찾는다 — 그리고 그 실패는 크래시가 아니라 "물이 좀 묽어진" 모습으로만 나타난다. 뒤에 Hybrid Tiled 키를 도입할 때 solver·anisotropy·boundary 등 격자를 조회하는 모든 셰이더를 같은 커밋에서 함께 고쳐야 했던 이유다.

이웃 탐색의 구조 — 실제 코드는 27셀이 매크로로 펼쳐져 있다5단계
int3 CenterCell = int3(floor(Pos / CellSize));
int  CellRadius = (int)ceil(SmoothingRadius / CellSize);   // CellSize == h 이므로 1

for (int dz = -CellRadius; dz <= CellRadius; ++dz)
for (int dy = -CellRadius; dy <= CellRadius; ++dy)
for (int dx = -CellRadius; dx <= CellRadius; ++dx)
{
    int3 NeighborCell = CenterCell + int3(dx, dy, dz);

    // 1단계와 똑같은 키 함수 — 여기가 어긋나면 이웃을 조용히 놓친다
    uint CellID = GetMortonCellIDFromCellCoord(NeighborCell);

    uint Begin = CellStart[CellID];
    uint End   = CellEnd[CellID];
    if (Begin == INVALID_INDEX) { continue; }              // 빈 셀

    for (uint j = Begin; j <= End; ++j)                    // 연속 구간 순회
    {
        float3 R  = Pos - Particles[j].PredictedPosition;
        float  R2 = dot(R, R);
        if (R2 < h2)                                       // 셀은 정육면체, 커널은 구
        {
            AccumulateDensityAndLambda(j, R, R2);
        }
    }
}

안쪽 루프가 이 파이프라인의 결과물이다. j가 연속으로 증가하므로 GPU의 캐시가 다음에 읽을 입자를 미리 끌어다 놓는다. 1장에서 매번 흩어져 있던 그 읽기가, 여기서는 순차 읽기가 됐다. 그리고 구간의 길이에 상한이 없으므로 밀집 구간에서 이웃이 잘려나가지도 않는다.

범위 메모

위 다섯 단계는 도입 시점의 설계다. 당시 radix는 pass당 4비트(16버킷)였고, 현재 코드의 8비트(256버킷) radix와 wave intrinsics, 그리고 5단계 안쪽 루프의 LDS 타일링·SoA 레이아웃은 이후 팀원들이 올린 별도 최적화다. 이 문서는 자료구조 설계 쪽만 다룬다.

04 검증/같은 커밋에 함께 넣은 디버그 도구

정렬이 실제로 됐는지 눈으로 본다

이런 종류의 변경은 틀려도 조용히 틀린다. 유체는 여전히 흐르고, 크래시도 없고, 이웃 몇 개가 빠진 결과는 "물이 좀 묽어졌나" 정도로 보인다. 그래서 정렬 파이프라인과 같은 커밋에 검증 도구를 함께 넣었다.

방법은 단순하다. 입자를 배열 인덱스에 비례한 HSV 무지개로 칠한다. 정렬이 제대로 됐다면 배열 인덱스는 곧 공간 순서이므로, 같은 색이 공간에서 덩어리로 뭉쳐 보여야 한다.

이 도구가 한 번 조용히 깨졌다

초기 시각화는 "readback 배열의 i번째 = 정렬된 배열의 i번째"라는 암묵적 전제 위에 있었다. 이후 readback 경로가 ParticleID 순서로 재정렬해 넘기도록 바뀌면서 그 전제가 끊겼고, 컴파일 에러도 크래시도 없이 시각화만 무의미한 그림이 됐다. GPU에서 ParticleID → ArrayIndex 매핑 버퍼를 따로 기록해 복구했다(9a1f358). 도구가 기대는 invariant는 코드에 적어두지 않으면 남이 모르고 깬다.

05 정제/2026-01-14 · 55015f9 → 3eb412d

정렬 키의 폭과 셀 배열의 크기를 일치시키다

도입 직후 코드에는 타협이 하나 남아 있었다. CellStart/CellEnd 배열은 MAX_CELLS = 65,536칸으로 고정돼 있는데, Morton 코드는 축당 10비트라 30비트였다. 셀 배열을 인덱싱하려면 코드를 잘라야 하고, 자른 값으로 정렬해야 같은 셀이 연속으로 모인다. 그래서 정렬 전에 하위 16비트만 남겼다.

FluidMortonCode.usf · 7470af5 시점타협
uint mortonCode = Morton3DFromCell(cellCoord, gridMin);   // 30 bit

// 정렬 전에 cellID로 잘라야 같은 셀 입자가 정렬 후 연속이 된다
uint cellID = mortonCode & (MAX_CELLS - 1);               // 하위 16 bit

MortonCodes[idx] = cellID;

동작은 맞지만 대가가 있다. 상위 비트를 버리면 공간적으로 멀리 떨어진 셀들이 같은 cellID로 접힌다. 후보 목록에 엉뚱한 입자가 섞이고, SPH 거리 검사가 그걸 걸러내는 낭비가 매 프레임 반복된다. 게다가 CellSize는 사용자가 직접 입력하는 값이라(기본 20 cm), SPH의 SmoothingRadius와 어긋나면 셀당 입자 수가 폭증하거나 27셀이 텅 비었다.

같은 날 한 시간 간격으로 두 축을 각각 풀었다.

  • Auto Cell Size 55015f9 — CellSize를 EditAnywhere에서 VisibleAnywhere로 내리고 Preset->SmoothingRadius에서 도출한다. 사용자가 틀릴 수 있는 손잡이를 없앴다.
  • Grid Resolution Preset 3eb412d — 축당 비트 수를 셰이더 permutation(FGridResolutionDim)으로 가변화했다. 컴파일 타임 분기이므로 런타임 비용은 0이다.

핵심은 표의 마지막 두 열이 서로 맞물린다는 것이다. 축당 b비트면 키 폭은 3b이고 MAX_CELLS도 정확히 23b다. 자를 필요가 없어지므로 cellID == 키가 되고, 앞의 aliasing이 통째로 사라진다. 현재 셰이더 주석이 그 결과를 그대로 적고 있다 — "No truncation needed since MAX_CELLS = 128³ < 2²¹".

돌아보면

  • 조용히 실패하는 도구는 조용히 실패한다. 시각화가 기대던 invariant ("readback 배열의 i번째 = 정렬된 i번째")를 코드에 명시하지 않았고, 남이 그 전제를 바꾸자 아무 신호 없이 무의미해졌다. 도구가 기대는 전제는 주석이든 assert든 코드에 남겨야 한다.
  • 키 폭 = MAX_CELLS 비트 폭. 도입 첫날에는 16비트 truncation으로 우회했고, preset permutation으로 폭을 정합시켜 근본 해결했다. 이 등식은 Hybrid Tiled 키 설계에서 세 번째로 다시 등장한다.
