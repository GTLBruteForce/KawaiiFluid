01 전제/앞 문서가 남긴 것

여기서 출발한다

앞 문서에서 SPH neighbor search를 Morton code 정렬 위에 다시 지었다. 입자를 셀 좌표의 Morton code로 정렬하고, 정렬된 배열에서 셀마다 시작·끝 인덱스를 뽑아 CellStart/CellEnd 두 정수로 셀을 표현하는 구조다. 이 문서를 읽는 데 필요한 전제는 두 가지뿐이다.

  • 정렬 키의 유효 비트 폭 = MAX_CELLS의 비트 폭. CellStart/CellEnd는 cellID로 인덱싱되는 배열이고 정렬은 키로 한다. 키가 cellID보다 넓으면 같은 셀의 입자가 정렬 후 여러 덩어리로 쪼개져 구간 검출이 깨진다. 이 등식이 이 문서의 설계 전체를 지배한다.
  • 격자 해상도는 셰이더 permutation으로 고른다. 축당 비트 수가 preset으로 정해지고, 키 폭과 MAX_CELLS가 그에 맞춰 함께 움직인다.

02 한계/Classic Morton의 구조적 제약

격자에 원점이 있는 한, 세계에는 끝이 있다

Classic Morton은 GridMin = floor(BoundsMin / CellSize)를 원점으로 삼고, 거기서의 오프셋을 0…MORTON_MAX_VALUE로 clamp해서 인코딩한다. 바꿔 말하면 bounds 밖 입자는 전부 가장자리 셀로 뭉개진다. 그래서 볼륨 크기 자체를 격자 용량에 맞춰 강제로 잘라야 했다(ClampExtentToMaxSupported).

그 상한이 위 표의 마지막 열이다 — 기본값인 Medium에서 25.6 m, Large를 써도 51.2 m가 끝이다. 그리고 이 상한은 넓히기 어렵다 — 범위를 키우려면 CellSize를 키워야 하는데, CellSize는 방금 SmoothingRadius에 묶어놓은 값이고, 키우면 셀 하나가 품는 입자가 늘어 탐색 비용이 그만큼 오른다.

막힌 지점

시뮬레이션 범위와 cache locality가 같은 손잡이(CellSize)에 묶여 있었다. 캐릭터에 붙어 월드를 자유롭게 돌아다니는 유체는 이 구조로는 불가능하다.

03 확장/2026-02-01 · 4b6f6c9

Hybrid Tiled Z-Order — 타일 안은 정확히, 타일 자체는 해시로

trade-off를 깨는 관찰은 이렇다. cache locality가 필요한 범위는 이웃 반경만큼, 즉 몇 셀 안쪽이다. 그보다 멀리 있는 입자끼리는 배열에서 붙어 있어봐야 아무 이득이 없다. 그렇다면 전체 월드를 하나의 Morton 공간에 인코딩할 이유도 없다.

그래서 키를 두 부분으로 쪼갰다. 하위 18비트는 64³ 타일 내부의 정확한 Morton 코드, 상위 3비트는 타일 좌표의 해시. 타일 내부는 종전대로 완벽히 코히어런트하고, 타일 자체는 좌표가 얼마든 해시로 접히므로 좌표 범위에 상한이 없다.

KawaiiFluidMortonUtils.ush · ComputeHybridTiledKeyAfter
uint ComputeHybridTiledKey(int3 GridPos)
{
    // 1) 타일 내부 좌표 — 비트 마스크가 음수를 알아서 처리한다
    uint3 LocalPos = uint3(GridPos.x, GridPos.y, GridPos.z) & HYBRID_TILE_MASK;   // 0..63

    // 2) 18-bit 지역 Morton
    uint LocalMorton = Morton3D_6bit(LocalPos.x, LocalPos.y, LocalPos.z);

    // 3) 타일 좌표 — 산술 우측 시프트로 부호 보존, (-5) >> 6 == -1
    int3 TilePos = int3(GridPos.x >> HYBRID_TILE_BITS,
                        GridPos.y >> HYBRID_TILE_BITS,
                        GridPos.z >> HYBRID_TILE_BITS);

    // 4) 타일 좌표를 3-bit로 해시 — 8 버킷
    uint TileHash = HashTile(TilePos) & HYBRID_TILE_HASH_MASK;

    // 5) 21-bit 키
    return (TileHash << HYBRID_LOCAL_MORTON_BITS) | LocalMorton;
}

타일 버킷이 8개뿐이라 충돌은 흔하다. 하지만 충돌은 정확성 문제가 아니라 비용 문제다 — 다른 타일에서 섞여 들어온 입자는 SPH의 거리 검사 r² < h²에서 그대로 탈락한다. 실제 유체는 국소적으로 뭉쳐 있어 동시에 활성인 타일 수가 적다는 점도 이 선택을 지탱한다.

이 모드가 켜지면 볼륨 크기 clamp가 통째로 빠지고, 볼륨 박스 자체를 끄는 bUseUnlimitedSize 옵션이 열린다. 현재 기본값은 Hybrid 켜짐이다.

04 제약/2026-02-04 · 54fc949

왜 32비트가 아니라 정확히 21비트인가

타일 해시에 비트를 더 주면 충돌이 줄어든다. 그런데 3비트로 못 박은 이유가 있다. 이 시스템 전체가 하나의 등식 위에 서 있기 때문이다 — 정렬 키의 유효 비트 폭 = MAX_CELLS의 비트 폭.

ComputeCellStartEndCS는 정렬된 배열을 한 번 훑으며 값이 바뀌는 지점에 CellStart[CellID] = Idx를 쓴다. 이 로직은 같은 cellID가 배열에서 한 덩어리라는 전제 위에서만 맞다. 키가 cellID보다 넓으면 정렬은 상위 비트를 먼저 보므로, 같은 cellID가 여러 덩어리로 쪼개진다. 그러면 뒤 덩어리가 앞 덩어리의 CellStart를 덮어쓰고 — 앞 덩어리의 입자들은 그대로 사라진다.

같은 등식이 앞 문서의 16비트 truncation과 preset 정합, 그리고 여기 Hybrid 키의 3+18 분할을 전부 설명한다. Hybrid 모드에서 grid preset을 Medium(2²¹)으로 강제하는 것도 그래서다 — 사용자가 Small을 골라도 21비트 키가 잘려나가지 않도록 54fc949에서 못을 박았다.

KawaiiFluidZOrderSortManager.hAfter
EGridResolutionPreset GetEffectiveGridResolutionPreset() const
{
    // Hybrid 키는 항상 21 bit — MAX_CELLS도 2^21이어야 한다
    return bUseHybridTiledZOrder ? EGridResolutionPreset::Medium
                                 : GridResolutionPreset;
}

측정하지 않은 이유

이 작업은 빨라지는 변경이 아니라 불가능하던 것을 가능하게 만드는 변경이다. 같은 bounds 안에서는 Classic과 Hybrid이 하는 일이 사실상 같고, bounds 밖에서는 Classic에 비교 대상이 없다. 그래서 sim ms A/B를 만들지 않았다 — 비교군이 성립하지 않는 구간에서 숫자를 만들면 그 숫자가 무엇을 뜻하는지 설명할 수 없다.

다만 비용이 없지는 않다. 타일 버킷이 8개뿐이라 서로 먼 타일의 입자가 같은 cellID로 섞여 들어오고, 그만큼 거리 검사가 헛돈다. 정확성 문제는 아니지만 (거리 검사 r² < h²가 걸러낸다) 후보 수가 늘어나는 비용은 실재한다. 이 오버헤드를 정량화하는 것이 남은 일이다.

돌아보면

  • 경계 조건을 요구사항에 넣지 않았다. Classic Morton의 bounds 상한은 캐릭터 부착 시나리오가 나온 뒤에야 문제로 인식됐다. "시뮬레이션 범위는 무한할 수 있다"를 처음부터 적어뒀다면 Hybrid 키를 한 번의 설계로 도달했을 것이다.
  • 같은 등식이 세 번 나타났다. 키 폭 = MAX_CELLS 비트 폭. 처음엔 truncation으로 우회했고, preset으로 정합을 맞췄고, Hybrid 키를 그 제약에 맞춰 설계했다. GPU 정렬 기반 공간 분할에서는 이 등식이 자료구조의 중심이라는 걸 세 번째에야 명제로 적었다.

이 문서는 Hybrid Tiled 키 설계 범위만 다룬다. 정렬 파이프라인 자체와 그 성능 측정은 앞 문서에 있다.
